# 重复值处理修订说明（2026-10-26）

## 新旧口径

旧版把用户、商品、行为类型、小时四元组相同的记录全部合并为一条。
这会合并普通重复交互。新版取消正常记录的四元组唯一性要求，保留真实操作频次。
仅在操作量和第二项异常证据同时满足的用户小时内，隔离重复冗余。
每个不同用户、商品、行为和小时的组合仍至少保留一条，不删除整个小时的全部行为。

原始 CSV、旧版清洗结果、旧 SQLite 和旧周报均不覆盖。旧版统计只适用于旧清洗口径。

## 自适应判定规则

1. 在全量非零用户小时分布上计算操作量阈值：
   `ceil(max(P99.9, Q3 + 3 * IQR))`，本次得到 **206**。
2. 在每个用户小时的“同商品同行为最大重复次数”分布上使用同样公式，得到 **12**。
3. 对每个用户的活跃小时计数计算中位数 m 和中位数绝对偏差 MAD，
   个人上界为 `max(3*m, m + 6*1.4826*MAD)`。
   个人基线只含该用户有操作的小时，不把零操作小时混入。
4. 当小时总操作量 **大于 206**，且满足以下任一条件时，标记为需要处理的异常小时：
   - 用户有至少 12 个活跃小时，且本小时操作量超过个人上界；
   - 本小时同商品同行为的最大重复次数 **大于 12**。
5. 仅对这些异常小时的重复四元组保留源文件顺序中的第一条，其他重复记录隔离至
   `removed_anomalies.parquet`。不同商品、不同类型、不同小时的独立组合全部保留。

分位数随每次输入数据重新计算，不把 206 或 12 固化为通用业务阈值。
P99.9、三倍中位数、六倍稳健标准差、最少 12 个活跃小时是透明的保守规则参数，
不是有真实机器人标签训练得到的判别边界；参数见 BurstRules。
统计异常并不等于已经证实为机器人、欺诈或系统重复上报。
高频但没有第二项证据的小时只标记，不自动压缩。

本轮诊断中超过 206 次的候选为 676 个用户小时；二次判断命中 417 个小时、268 个用户。
这些小时共有 108,299 条操作，其中重复冗余 52,576 条。

## 运行与复现

当前电脑在 Anaconda PowerShell Prompt 中运行：

```powershell
python 'D:\字节\behavior_cleaning\run_cleaning.py'
```

默认使用新版 `--repeat-policy burst`。如需复现旧口径，显式使用
`--repeat-policy legacy`。迁移到其他电脑时先安装 requirements.txt，
新版增加 DuckDB 作为可落盘的分组统计与 Parquet 导出引擎。

新版仍使用相同的字段校验与分块读取，使用 DuckDB 计算全局重复、个人基线和聚合，
待处理块数受 workers 限制，分析引擎内存预算约 1 GB，超出部分允许落盘。
代码不执行近似分位数抽样，也不使用块内去重替代全局规则。

| repeat_gap_hours.parquet | 同用户商品行为在不同小时桶之间的观测间隔 |
| repetition_analysis.json | 原始频次、分位数和跨小时重复间隔摘要 |

新版通过“输入=规则拒绝+异常冗余隔离+保留”核对总量，同时核验 Parquet 行数、
用户/商品/时间三个聚合总量、全部独立操作组合未丢失及隔离只发生在异常小时。
重复冗余的“观测数”“隔离数”和“保留数”分别报告，不再把观测到的重复都算成删除。

## 下游影响

之前的 SQLite 数据库仍是旧清洗口径，不会自动更新。需要分析新版数据时，运行
`scripts/build_database.py`，该脚本会识别新版报告，采用普通四元组索引，
正常重复通过独立 event_id 保留，默认另存至 outputs/sql_analysis_v2/。
已有同名数据库仍禁止覆盖。旧版报告或无新版政策标记的输入仍按旧唯一约束处理。

本次只重跑清洗和三个维度聚合，不自动重建约 1.55 GB 的旧 SQLite。
以后业务统计、特征和周报需从新版数据重新计算，不能与旧口径计数混用。

异常阈值和个人基线当前拟合于整个已观察数据集，适合本次描述性清洗。
若用于未来七天购买预测，应只在训练历史期拟合阈值，并固定后应用于验证/测试，
避免使用未来行为来决定过去样本的清洗方式。
